# Phase 2.2 — Media References & Seamless Serving Implementation Plan

**Roadmap:** `docs/superpowers/specs/2026-09-26-completion-roadmap.md` → Milestone 2 → 2.2 (design in §3.6, §3.7)

**Goal:** Photos and videos live in each family's Immich account; Werejugo keeps a reference plus a small metadata cache for each one.
- Everything in the family's Immich account appears in Werejugo within minutes, including photos added in Immich directly.
- Edits and deletions follow.
- The browser never talks to Immich. Werejugo serves thumbnails, previews, originals and video at its own cacheable, signed URLs, with seeking.
- Uploading through Werejugo hands the file to Immich. 2.3 makes uploads chunked and resumable; this phase keeps the current 25 MB single request.

**Decisions this plan relies on:**
- **§2:** Immich is the photo store; test data only, so the local photo files aren't migrated.
- **§2 (2026-09-27):** uploads go through Werejugo; Werejugo sees photos added in Immich directly.
- **§3.6:** reference table + metadata cache + sync job; proxied media with Range; cacheable signed links.
- **§3.7:** pg-boss on the existing Postgres.

---

### Data model (migration `0005_media_on_immich.sql`)

- `media` becomes a reference to an Immich asset:
  - **Kept:** `id` (Werejugo's id, so links, avatars and trips keep working), `family_id`, `trip_id`, `kind` (image|video), `caption`, `taken_at`, `geom`, `width`, `height`, `created_by`, `created_at`.
  - **New:** `immich_asset_id UUID NOT NULL UNIQUE`, `original_name`, `mime`, `bytes`, `duration_ms`, `thumbhash`, `immich_updated_at`, `synced_at`.
  - **Dropped:** `rel_path`, `thumb_rel_path`.
- **Existing rows are deleted** (test data; §2). Their links and avatars go through the existing triggers and `ON DELETE SET NULL`. Old files stay on disk under `families/<id>/…/photos` until the admin removes them (README).
- `family_immich` gains sync state: `sync_since`, `last_sync_at`, `last_full_sync_at`, `sync_error`, `asset_count`.

### Adapter additions (`lib/immich/client.ts`, contract-tested)

- `uploadAsset(conn, file, {filename, fileCreatedAt, fileModifiedAt})` → `{id, status: created|duplicate}`.
- `getAsset(conn, id)`.
- `searchAssets(conn, {filter, cursor, size, withExif})`, using the 3.2 structured search (`filter`, `cursor`).
- `trashAssets(conn, ids)` (`DELETE /assets`, force=false: Immich keeps it in its trash).
- `setDescription(conn, id, text)` (`PUT /assets/:id`: deprecated in 3.2, but it's the only way to set a description and works until 4.0; the contract test will catch its removal).
- `fetchMedia(conn, id, size, {range, ifNoneMatch})` → the raw streaming `Response`:
  - `thumbnail` → `/thumbnail?size=thumbnail`
  - `preview` → `/thumbnail?size=preview`
  - `original` → `/original`
  - `video` → `/video/playback`
- **Contract tests** (stand-in and real Immich):
  - Upload a JPEG → created, then again → duplicate.
  - Info and search find it.
  - Thumbnail/preview/original bytes, and `Range: bytes=0-9` on the original → 206 with `Content-Range`.
  - Setting a description shows up in info and search.
  - Trash → gone from the default search and found by a `trashedAt` filter.
  - Updated-since search.

### Serving

- **Signed URLs:** `signMediaUrl(mediaId, size)` → `/api/m/<mediaId>/<size>?e=<expiry>&s=<hmac>`.
  - Expiry is **bucketed** (valid 24–30 h, changing every 6 h), so the same photo has the same URL for hours and the browser cache works (fixes the every-request signatures).
  - The signature covers id, size and expiry.
- **Proxy route** `GET /api/m/:id/:size` (no session; the signature is the permission):
  - Verify the signature → look up the row → use the media's own family key (cached for 60 s in memory) → fetch from Immich.
  - Stream back with `Content-Type`/`Length`/`Range`, `Accept-Ranges`, `ETag` and `Last-Modified`, answering 200, 206 or 304.
  - `Cache-Control: private, max-age=<until expiry>` (originals: `no-store`, `Content-Disposition: attachment; filename=…`).
  - A photo whose Immich asset is gone → 404, and the reference is removed on the next sync.
- DTOs everywhere carry `thumbUrl`, `url` (preview), `originalUrl`, `videoUrl` (videos), `kind`, `takenAt`, `lat/lng`, `width/height`, `durationMs`, `caption`, `familyId`, `familyName`:
  - Photos list/detail, visit photos, avatars, relations, search, public share pages.
- `/api/files` stays for documents only.

### Upload (single request here; chunked in 2.3)

`POST /api/media` (multipart, 25 MB):
1. Read EXIF locally (date, GPS) for immediate suggestions.
2. Hand the file to Immich with the family's key.
3. `created` → insert the reference with local EXIF and whatever Immich already knows (Immich finishes its own metadata a few seconds later; the next sync refines it).
4. `duplicate` → return the existing reference with `duplicate: true` ("already in your library").
- No Immich connection → 409 "Photos need Immich — ask the server admin to connect your family".

### Changes to what already exists

- **Caption:** it lives in Immich as the asset's description. PATCH writes it; sync reads it.
- **Delete:** `DELETE /api/media/:id` moves the asset to Immich's trash (restorable there for 30 days) and removes the reference.
- **Trips and visits:** trip changes and visit links no longer move files; `trip_id` is just a column. The storage-folder logic (`mediaDirFor`, `reconcileMediaTrip`) and the sharp thumbnails for media are removed.
- **Other routes:**
  - Family export: media rows, with a note that the photos themselves are in the family's Immich account.
  - Admin family delete: no media files to delete.
  - Backup: media rows only (the photos are backed up with Immich, per the guide).

### Sync (pg-boss)

- **pg-boss 12** on the existing database (its own `pgboss` schema), started by the server (not in tests; tests call the job functions directly).
- **`immich.sync` every 5 minutes:** for each connected family, an incremental sync.
  - Search `updatedAt > since` (with EXIF), upsert references (IMAGE/VIDEO; `hidden`/`locked` visibility skipped).
  - Assets trashed since `since` are removed.
  - `since` = run start − 2 min (overlap; upserts are idempotent).
- **`immich.reconcile` nightly (and for a family's first sync):** list every asset id, upsert, and remove references to assets no longer in the account. References created during the run are kept.
- **Admin → Immich:** each family's last sync, photo count and error, plus a **Sync now** button (queues both). The family's Photos page offers "Refresh from Immich" (incremental sync, rate-limited).
- A family's first connection queues its full sync right away.

### Frontend

- The **Photos page** without Immich shows "Photos need Immich" (with the admin link for admins) instead of the library.
- **Videos** play from `videoUrl` in the lightbox, with seeking.
- **Photo detail** gains "Download original".
- Grid thumbnails and the lightbox use `thumbUrl`/`url`.
- Upload review shows "Already in your library" for duplicates.
- The share view and command palette get photo URLs that work under `API_URL` (fixes an Appendix A.3 item).

### Tests

- **Adapter:** the contract tests above, run against the stand-in and a real Immich in CI.
- **Media routes:**
  - Upload hands the file to Immich; duplicates; no connection → 409; list/filter/cursor unchanged.
  - Caption round trip; delete trashes the asset.
  - A trip change doesn't touch files.
- **Proxy:**
  - A bad or expired signature → 403.
  - Range → 206; `If-None-Match` → 304; cache headers; originals as attachments.
  - Another family's media id with a valid signature is served only because the signature says so (signatures are issued only for readable media).
- **Sync:**
  - New, updated, trashed and deleted assets; hidden and locked skipped; idempotent.
  - The reconcile keeps in-flight uploads.
  - Errors are recorded per family.
- **Everything already covering media:** visits, people avatars, relations, search, share pages, family export, backups, the isolation suite (media cases now via the stand-in).
- **Playwright against the stand-in:**
  - Upload a photo → it shows in the grid, lightbox and a place.
  - A photo added "in Immich" (the stand-in's API) appears after sync.
  - A video seeks.
  - The public share page shows photos.
  - Phone and desktop.
