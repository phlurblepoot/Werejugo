# Phase 2.8 — Smart Search & Smart Albums Implementation Plan

**Roadmap:** `docs/superpowers/specs/2026-09-26-completion-roadmap.md` → Milestone 2 → 2.8 (design in §3.6)

**Goal:** find photos by what's in them, and keep a search as an album.
- Type "beach at sunset" in the command palette or on the Photos page, and get the matching photos. This is Immich's smart search (CLIP), combined with Werejugo's filters (person, trip, place, dates, photos/videos).
- **Save as smart album** keeps the search and the filters under a name. It fills itself as photos arrive, opens from the Photos page, and can be shared by a public link like a trip's album.

**Decisions this plan relies on:**
- **§2 (2026-09-27):** stock Immich. Its smart search needs Immich's machine learning container, which the Unraid guide installs (with the RTX 5070).
- **1.x share links:** public, read-only, revocable (`share_links`).

---

### Constraints found while planning

- **Smart search needs Immich's machine learning.** CI's Immich runs without it (the image is too big for CI), and the real Immich then refuses: `400 Smart search is not enabled`.
  - The contract test checks that refusal, and that the request is otherwise well-formed.
  - The stand-in does both. It has machine learning "off" for the contract. With it "on" (development and Playwright), it matches words against the photo's description, file name and place name.
  - Werejugo says, when it's off: "Smart search needs Immich's machine learning, which is turned off on your Immich server."
- **Results come in Immich's relevance order,** 100 a page. Werejugo keeps the ones in the family's library that match its own filters (hidden photos are left out), in that order. A page can come back with fewer than 100; "More" asks for Immich's next page.
- **A smart album is a saved filter, not a list of photos.** It's evaluated when it's opened, so it "updates automatically". Opening one in the app sets the Photos page's filters and search. A public link evaluates it on the server (at most 500 photos, newest first; relevance order with a search).
- **Share links** gain a target type `smart_album` (migration: the CHECK constraint, and deleting a smart album deletes its links, as with trips).
- **Bug found while planning:** a public album link shows photos hidden from the library. Hidden photos are left out of every public link from now on (logged).

### Data model (migration `0011_smart_albums.sql`)

- **`smart_albums`:** `(id, family_id → families ON DELETE CASCADE, name, filters JSONB, created_by → users, created_at, updated_at)`.
  - `filters` holds the same keys as the library's filters (`person`, `trip`, `visit`, `from`, `to`, `kind`, `noTrip`) plus `q`, the smart-search text.
- `share_links.target_type` also allows `smart_album`; a trigger deletes an album's links with it.

### Adapter and contract

- `immich.smartSearch(conn, { query, page, size, type?, takenAfter?, takenBefore? })` → `{ items, nextPage }`.
- **Contract:**
  - Real Immich without machine learning: the request is refused with "Smart search is not enabled" (a 400 that names machine learning, not a validation error).
  - Stand-in: the same with its machine learning off.
- **Stand-in:** `POST /api/search/smart`. With machine learning on, it's a word match over description, file name and city, paged.

### API

| Route | What it does |
|---|---|
| `GET /api/media/search?q=…&page=&filters` | Smart search within my library: `{ items: MediaItem[], nextPage }`. With machine learning off: 409 with the explanation. With no Immich: 503. |
| `GET /api/smart-albums` | My family's smart albums. |
| `POST /api/smart-albums` | `{ name, filters }`. Ids in the filters are checked with `assertRefs` (a person, trip or place I can see). |
| `PATCH /api/smart-albums/:id` | Rename, or new filters. |
| `DELETE /api/smart-albums/:id` | Deletes it, and its share links. |
| `POST /api/shares` | `targetType: "smart_album"` too. |
| `GET /api/share/:token` | For a smart album: `{ targetType, album: { name }, photos }`, evaluated now. |

- **Isolation cases** for every route; another family's album or ids are a 404 or 400.

### Frontend

- **Command palette:** a **Photos** group for queries of 3 characters or more: up to 6 thumbnails from smart search, and "All photos matching '…'" → `/photos?q=…`. When smart search is off, the group says so once.
- **Photos page:**
  - A search field. With text, the grid shows the results in relevance order (with **More**) instead of the timeline, and the filters still apply.
  - `/photos?q=` opens a search.
  - **Save as smart album** appears when there's a search or a filter.
  - A **Smart albums** menu: open one (`/photos?album=<id>` sets its filters and search), rename, share (the share dialog), delete.
- **Public link page:** a smart album shows its name and photos, like a trip's album.

## Outcome (2026-09-27)

Built as planned, with these differences and findings:

- **Machine learning off** is a 409 from `/api/media/search` (the request was fine; the server can't do it). A 503 means there's no Immich at all. The palette and the Photos page explain the 409.
- **The palette's group is "In your photos"** (up to 6 thumbnails, then "All photos of …"). It sits beside the existing caption-based "Photos" group. It searches 300 ms after typing stops, from 3 characters, because each search runs Immich's machine learning.
- **The Photos page follows `?q=` and `?album=`** while it's open. It had only read them when it first opened, so the palette's link didn't search when you were already there.
- **Opening a smart album** sets the page's filters and search. The album bar offers **Update album** when they've changed since.
- **Public links** leave out hidden photos (trips, albums and smart albums). A smart album's link shows the family's own photos only, never another family's photos on a shared trip.
- **Empty filter fields** (for example a cleared date) are dropped before a smart album's filters are checked.
- **Verified:**
  - Backend 468/468 and frontend 266/266.
  - Contract against the real Immich without machine learning.
  - Playwright through nginx with the stand-in (machine learning on): 20 checks, desktop and phone.
