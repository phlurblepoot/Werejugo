# Phase 2.3 — Uploads at Scale Implementation Plan

**Roadmap:** `docs/superpowers/specs/2026-09-26-completion-roadmap.md` → Milestone 2 → 2.3 (design in §3.6)

**Goal:** a family can drop a whole card of photos and long phone videos into Werejugo, from home or through Cloudflare, and every file arrives in its Immich account.
- Files go up in small chunks. A dropped connection or a closed laptop resumes where it stopped, not from zero.
- Each file shows its own progress, and a failed file can be retried on its own.
- Once the bytes are in, Werejugo hands the file to Immich in the background. The person can leave the page; the photo still arrives, linked to the place or person it was added to.
- iPhone HEIC, Live Photos, camera RAW and video go to Immich as they are. Immich decodes them, makes thumbnails and transcodes video.
- A file already in the library says "Already in your library" instead of making a copy.

**Decisions this plan relies on:**
- **§2 (2026-09-27):** uploads go through Werejugo.
- **§3.6:** chunked, resumable uploads (tus-style); every request well under Cloudflare's 100 MB cap; Werejugo hands the assembled file to Immich over the LAN.
- **§3.7:** pg-boss for background work.

---

### Constraints found while planning

- **Cloudflare:** its free plan refuses request bodies over 100 MB. Chunks are **8 MiB**: a slow phone connection loses little when a chunk fails, and the per-request overhead is small. The server accepts chunks up to 32 MiB.
- **Browsers can't re-open a file by themselves.** After a page reload, an unfinished upload can only continue once the person picks the same file again. Werejugo recognises it by name, size and modification time, and continues from the last byte received.
- **Upload progress:** `fetch` can't report upload progress, so chunks are sent with `XMLHttpRequest`, which can.
- **Memory:** a 4 GB video must not be held in memory. Chunks stream straight to a file on disk. The hand-off streams that file to Immich (`fs.openAsBlob`, Node 22), and EXIF is read from the file path, which reads only the start.
- **Duplicates in Immich:** uploading a file that's already there returns `duplicate` with the existing asset's id, **including when that asset is in Immich's trash**. Werejugo restores it from the trash, since the person clearly wants it (contract-tested).
- **Live Photos:** Immich pairs a photo with its motion clip by itself (from their shared content identifier) and hides the clip. Werejugo doesn't pair anything. It just has to drop a reference once its asset becomes hidden. Today that happens only in the nightly full sync; the 5-minute sync will now also remove references to assets that became hidden or locked.
- **iPhone Safari:** Safari's photo picker usually converts HEIC to JPEG and sends only the still of a Live Photo. Werejugo keeps whatever the browser sends. Full-quality HEIC and Live Photos come in through Immich's own app (they appear through the library sync), or from a computer.

### Data model (migration `0006_media_uploads.sql`)

- **`media_uploads`:** one row per file being uploaded.
  - **Who and what:** `id`, `family_id`, `user_id` (`ON DELETE SET NULL`), `filename`, `mime`, `size` (bigint), `file_modified_at`.
  - **Where to put it:** `caption`, `link_to` (an entity reference like `visit:<id>`), `link_role`.
  - **Progress:** `received` (bigint), `state` (`receiving` | `processing` | `done` | `failed`).
  - **Result:** `media_id` (`ON DELETE SET NULL`), `duplicate`, `error`.
  - **Times:** `created_at`, `updated_at`.
- Index: `(family_id, user_id, state)`.
- The bytes live at `UPLOADS_DIR/incoming/<id>.part` until Immich has them.

### API (`routes/media-uploads.ts`, all family-scoped, 404 for anyone else's upload)

| Route | What it does |
|---|---|
| `POST /api/media/uploads` | `{filename, size, mime, lastModified?, caption?, linkTo?, linkRole?}` → 201 `{id, chunkSize, offset: 0, state}`. It checks, in this order, then creates the row and an empty file: Immich is connected (409 "Photos need Immich…"); it's a photo or video, by type or extension (400); the size is at most `MAX_UPLOAD_GB` (default 20; 400); and `linkTo` is valid and editable (400 "Unknown …", via `assertRefs`). |
| `PUT /api/media/uploads/:id?offset=N` | Body: `application/octet-stream`, at most 32 MiB. If `offset` isn't the number of bytes already received, it answers 409 `{error, offset}` so the client can continue from there. Otherwise it streams the bytes into the file at that offset, then records the new total; a broken chunk records nothing and is simply sent again. At most `size` bytes are taken, never more. When the last byte arrives, the state becomes `processing` and the hand-off is queued. → `{offset, state}` |
| `GET /api/media/uploads/:id` | `{id, filename, size, offset, state, duplicate, error, media}`. `media` is the photo's full DTO once it's `done`. |
| `GET /api/media/uploads` | My uploads from the last 2 days that aren't done, plus those that finished in the last 10 minutes: the tray uses it after a reload. |
| `POST /api/media/uploads/:id/retry` | A `failed` upload whose bytes are still here is queued again; with no bytes on disk, 409 "Choose the file again". |
| `DELETE /api/media/uploads/:id` | Cancels: deletes the bytes and the row (409 while it's being handed to Immich). |

- A content-type parser for `application/octet-stream`, registered only inside this plugin, hands over the raw stream.
- Each upload takes one chunk at a time, through an in-process lock and a conditional `UPDATE … WHERE received = $offset`.
- **nginx:** `location ^~ /api/media/uploads/` with `client_max_body_size 40m`, `proxy_request_buffering off` (progress is real and nothing is written to temp files) and 300 s timeouts.

### The hand-off (`lib/media/handoff.ts`, pg-boss queue `media-upload-handoff`)

1. Load the row (`processing`) and the family's Immich connection. With no connection, it fails: "Photos need Immich…".
2. Read EXIF (date, GPS) from the file path.
3. Pick the file's date: the EXIF date, else the browser's `lastModified`, else now.
4. Upload to Immich with `fs.openAsBlob(path)` (streamed). The time limit grows with the size: at least 10 minutes, plus 1 minute per 500 MB.
5. On `duplicate`, get the asset. If it's in Immich's trash, restore it (`POST /trash/restore/assets`).
6. `upsertAsset`, using the local EXIF as the fallback (the same as `POST /api/media` today). Save the caption to Immich if there is one.
7. If `link_to` is set, `createLink` with the uploader's scope, built from the `users` row. If the uploader is gone, the link is skipped.
8. Set the row to `done`, with `media_id` and `duplicate`. Delete the file.

**Errors:**
- Immich *rejects* the file (for example "Unsupported file type"): the row becomes `failed` with Immich's reason, and the file is deleted. Retrying won't help, so the person is told why.
- Immich is unreachable or times out: pg-boss retries it 3 times (30 s, 60 s, 120 s). After the last try, the row becomes `failed` ("Couldn't reach Immich. Try again in a few minutes."). The file is kept, so **Retry** resends it without uploading again.
- Tests have no queue: the hand-off runs inline and `settleJobs()` waits for it, like the sync.

`POST /api/media` (a single multipart request of up to 25 MB) stays for API compatibility and shares steps 2–8 through `lib/media/import.ts`. The web app no longer uses it.

### Cleanup (pg-boss, daily `media-uploads-cleanup`)

- Uploads still `receiving` and untouched for 48 hours: the file and row are deleted.
- `failed` uploads older than 7 days: the file and row are deleted.
- `done` rows older than 1 day are deleted.
- Files in `incoming/` with no row are deleted, if they're older than an hour.

### Sync addition

- The incremental sync also looks for assets that became `hidden` or `locked` since the last sync, and drops their references. That covers Live Photo clips Immich paired after upload, and photos moved to Immich's locked folder.

### Adapter and contract additions

- `immich.restoreAssets(conn, ids)`.
- `uploadAsset` takes a `timeoutMs`.
- **Contract tests** (stand-in and real Immich):
  - Upload, trash, upload again → `duplicate` with the same id, and the asset says `isTrashed`. `restoreAssets` → it's no longer trashed.
  - A short WebM clip (a 1-second fixture recorded in Chromium, a few KB) → `type: VIDEO`, and its bytes are served at `/video/playback`.
  - An AVIF photo (made with sharp, HEIF container) → accepted as `IMAGE`.
  - Searching with `visibility in [hidden, locked]` works.
- **Stand-in:** restore from trash, `duplicate` for trashed assets, and video/AVIF names accepted.

### Frontend

- **`lib/uploads/` — the upload manager** (plain TypeScript with a small store, unit-tested without React):
  - `add(files, {linkTo?, linkRole?, caption?, batch?})` → queued tasks. Three files go up at a time; each file's chunks go one after another.
  - **Chunks:** sent with XHR, with progress. Network errors and 5xx answers retry with backoff (1 s, 2 s, 4 s, 8 s, 15 s, 30 s, then the file shows "failed", with Retry). A 409 continues from the server's offset. A 401 stops everything, as the app already does.
  - **Resume:** a map in `localStorage` from file fingerprint (name|size|lastModified) to upload id, per user. Adding a file that's already in the map asks the server for its offset and continues from there.
  - **After the bytes:** it polls `GET /api/media/uploads/:id` (1.5 s, slowing to 5 s) until `done` or `failed`, calls the batch callbacks, and invalidates the photo queries.
  - **On start:** it loads `GET /api/media/uploads`, so an upload interrupted by a reload shows as "Paused — choose the file again to finish (45% sent)", and one still being handed to Immich keeps being tracked.
  - While bytes are still being sent, leaving the page asks first (`beforeunload`).
- **`UploadsProvider` + `useUploads()`,** mounted in the app shell, so uploads carry on across pages.
- **`UploadTray`** (kit styles; bottom-right card on desktop, above the bottom tabs on phones):
  - Header: "Uploading 3 of 10 · 45%" or "10 uploaded", with collapse and "Clear finished".
  - One row per file, with name, size and a progress bar. The status reads:
    - "Sending 12 of 80 MB"
    - "Adding to Immich…"
    - "Added"
    - "Already in your library"
    - "Failed: reason", with **Retry**
    - "Paused — choose the file again", with **Choose file**
  - Each row has a cancel ✕.
  - Screen readers get a polite live region for "10 uploaded" and failures.
- **Callers move to the manager:**
  - `MediaUploader`: its `onUploaded` and `onAllUploaded` fire as files finish. Links are made on the server through `linkTo`.
  - Photos page: "Upload" still opens the suggestions review when a batch finishes.
  - `VisitEditor`: staged photos no longer hold the editor open while they upload. Saving queues them with `linkTo: visit:<id>` and closes the editor, and the tray shows the rest.
  - `PersonForm`: the avatar waits for its one file.
- The photo pickers keep accepting HEIC/HEIF, RAW and video (`MEDIA_ACCEPT`). A file that isn't a photo or video is refused before any bytes are sent.

## Outcome (2026-09-27)

Built as planned, with these differences and findings:

- **The upload to Immich is streamed with `node:http`.** Measuring showed that Node's `fetch` (and so the SDK's `uploadAsset`) holds a whole request body in memory: a 600 MB file peaked at 720 MB of memory. `immich.uploadAsset` now sends the same multipart request itself, streamed from the file; the same file peaks at 133 MB. Unit tests cover the request's shape, Immich refusing a file before reading it all, and a timeout; the contract tests (stand-in and real Immich) use it for every upload.
- **The locked folder can't be searched (found by the contract test against the real Immich 3.2.2).** Immich refuses a search for `locked` assets with a 401: its locked folder needs the PIN-unlocked session, which an API key never has. Asking for "hidden or locked" would have made every 5-minute sync fail. The sync asks for hidden assets only (Live Photo clips); photos moved to the locked folder leave at the nightly full sync. The stand-in refuses a locked search the same way.
- **nginx:** `location ^~ /api/media/uploads/` (with a trailing slash) made nginx answer `POST /api/media/uploads` itself with a 301. This showed up once the browser checks ran through the real nginx config (installed in the sandbox for this). The location has no trailing slash now.
- **The single-request upload stays** (`POST /api/media`, 25 MB), sharing `lib/media/import.ts` with the hand-off. The web app no longer uses it, and `api.uploadMedia` is gone from the frontend.
- **Order of checks when creating an upload:** type, size and link come before the Immich connection, so another family's place is a 400 whether or not Immich is connected (the isolation suite checks this).
- **Tray details:** a finished row can be hidden on its own; a paused upload is shown as a warning, not an error. The overall bar counts finished files in full.
- **Verified:**
  - Backend 372/372, including 13 upload route tests, the isolation cases, sync of newly hidden assets, and the streamed upload.
  - Frontend 216/216, including the manager against a fake server (pieces, retry, 409 offsets, resume after reload, three at a time, cancel) and the tray.
  - Playwright through nginx, the backend with its real job queue, and the stand-in: 21 checks.
    - A 40 MB photo went up in 5 pieces, with one piece dropped and resent.
    - A 36 MB video was reloaded half-way and resumed from 16 MB.
    - A duplicate, a refused text file, and a place photo linked after its editor closed.
    - Phone layout.
  - The contract test against the real Immich 3.2.2 in CI covers trashed duplicates and restore, a WebM clip and an AVIF photo.
