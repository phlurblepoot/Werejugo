# Phase 2.1 — Immich Connector & Provisioning Implementation Plan

**Roadmap:** `docs/superpowers/specs/2026-09-26-completion-roadmap.md` → Milestone 2 → 2.1 (design in §3.6)

**Goal:**
- The server admin connects Werejugo to the owner's Immich server once (address + an Immich admin API key).
- Werejugo then gives every family its own Immich account and key, or links an Immich account that already exists.
- Stored keys are encrypted.
- The admin page shows whether Immich is reachable, its version, and each family's connection.
- A family owner can set the family's Immich password to use Immich's own web page or app.
- A written guide installs Immich on Unraid with the owner's NVIDIA card.

Nothing moves photos yet (2.2+). This phase makes the connection safe, visible and tested.

**Decisions this plan relies on:**
- **§2 photo backend:** Immich stores the photos; each family has an account on the owner's Immich server; the browser never talks to Immich.
- **§2 photo uploads (2026-09-27):**
  - Uploads go through Werejugo.
  - Werejugo also sees photos added in Immich directly, so a family may have an Immich login.
- **§2 hardware:** NVIDIA RTX 5070.
- **§3.6:**
  - Admin URL + key.
  - Per-family user + key, encrypted.
  - One adapter module.
  - Pinned version range, startup version check, contract tests.

### Constraints found while planning

- **No Immich in the sandbox:** Immich's images live on ghcr.io, whose blob downloads the sandbox proxy blocks.
  - Development therefore uses a **stand-in Immich**: a small Fastify app in the test helpers that implements exactly the calls Werejugo makes, with response shapes copied from the Immich 3.2.2 OpenAPI spec.
  - A **CI job** starts the real `immich-server:v3.2.2` (plus its Postgres and Valkey; machine learning off) and runs the same contract tests against it.
- **Immich 3.2.2 facts** (from its spec and compose files):
  - `POST /api/admin/users` (needs `adminUser.create`) creates a user with email, name and password.
  - An admin key can't mint keys *for* another user. So Werejugo signs in as the new user once (`POST /api/auth/login`), creates that user's key (`POST /api/api-keys`, permissions `["all"]`; the secret is in `secret`, since `apiKey` is deprecated in 3.2), and forgets the password.
  - `PUT /api/admin/users/:id` can set a password later.
  - The version is at `GET /api/server/version`; the connection check is `GET /api/server/ping`; `GET /api/users/me` identifies a key.
- **Supported versions:** Immich **≥ 3.2.0 and < 4.0.0**. Anything else still works, but the admin page and the startup log warn about it.

### Secrets (`ENCRYPTION_KEY`)

- A new environment variable, `ENCRYPTION_KEY`, holds a long random string (`openssl rand -hex 32`). It's needed to turn Immich on, and 3.3 will reuse it for document files.
  - Missing, a placeholder or shorter than 32 characters: the Immich settings say what to do and refuse to save. Nothing else is affected.
- `lib/secretbox.ts`:
  - AES-256-GCM with a key derived by HKDF-SHA256 from `ENCRYPTION_KEY`.
  - Output format `v1:<base64 iv|tag|ciphertext>`.
  - `seal(text)` and `open(sealed)` (throws `SecretUnreadable` on a wrong key or tampering), `encryptionReady()`.
- **Backups:**
  - They carry the sealed keys, never plain ones.
  - Restoring onto a server with a different `ENCRYPTION_KEY` leaves them unreadable. The admin page then says "re-enter the admin key", and families are re-keyed automatically (see Health).

### Data model (migration `0004_immich.sql`)

- `immich_server` (at most one row):
  - `id` (always `true`), `url`, `admin_key_sealed`, `updated_at`, `updated_by`;
  - `last_check` (JSONB: ok, version, supported, error, at).
- `family_immich`:
  - `family_id` (PK, cascade), `mode` (`'created'` = Werejugo made the account, `'linked'` = an existing Immich account);
  - `immich_user_id` (unique), `immich_email`, `api_key_id`, `api_key_sealed`;
  - `created_at`, `last_ok_at`, `last_error`.
- Both tables go in `BACKUP_TABLES`. Neither goes in a family's own export: keys are server secrets.

### Adapter (`backend/src/lib/immich/`)

- `client.ts`:
  - Wraps the official `@immich/sdk@3.2.2` (typed functions generated from the same spec), with a per-call base URL, `x-api-key` header and 10-second timeout.
  - One function per operation we use: `ping`, `version`, `me`, `createUser`, `updateUser`, `login`, `createApiKey`, `deleteApiKey`.
  - Every call goes through here. Nothing else imports the SDK.
- `errors.ts` maps failures to messages a person can act on:
  - unreachable: "Werejugo can't reach Immich at …";
  - 401: "Immich rejected the key";
  - 403: "The key is missing permission X";
  - a version outside the range.
- `version.ts`: parse and compare versions, and `SUPPORTED_RANGE`.
- `provision.ts`, where the steps can fail part-way:
  - `provisionFamily(familyId)`: create the Immich user (email `<family-slug>-<6 hex>@werejugo.local`, name = family name, random 32-character password, `shouldChangePassword: false`) → log in as it → create the key "Werejugo" → seal and store it.
    - If a step after the user exists fails, it's recorded in `last_error`, and a retry reuses the user (found by email) and resets its password through the admin key.
  - `linkFamily(familyId, apiKey)`: check the key with `/users/me`, refuse one that's already linked to another family, and store it.
  - `unlinkFamily(familyId)`: delete Werejugo's key in Immich where possible, then drop the row. **The Immich account and its photos are never deleted by Werejugo.**
  - `rekeyFamily(familyId)`: used when the stored key is unreadable or rejected on a `created` account. It resets the password via the admin key and mints a new key.
- `health.ts`:
  - `checkServer()` → `{ok, version, supported, error}`, stored in `last_check`.
  - `checkFamily(familyId)` → `/users/me` with the family's key.

### API

**Admin** (`requireAdmin`; every change audit-logged):
- `GET /api/admin/immich`:
  - `{encryptionReady, configured, url, adminKeySet, check, supportedRange}`;
  - `families: [{id, name, state: 'none'|'created'|'linked'|'error', immichEmail, lastError, lastOkAt}]`.
- `PUT /api/admin/immich {url, adminKey?}`:
  - Checks the address and key live: ping, version, `/users/me` is an admin, and the key may create users. Then saves.
  - `adminKey` may be left out to keep the stored one.
  - Invalid → 400 with the reason.
- `POST /api/admin/immich/check`: re-runs the health check (server + every family).
- `POST /api/admin/immich/families/:id/connect`: provisions. Also used for "retry" and "re-key".
- `POST /api/admin/immich/families/:id/link {apiKey}`: links an existing account.
- `DELETE /api/admin/immich/families/:id`: unlinks (keeps the Immich account and photos).
- `POST /api/admin/immich/connect-all`: provisions every family without a connection; returns per-family results.

**Family:**
- `GET /api/immich` (any signed-in user): `{enabled}`, plus `{url, email, mode, canSetPassword}` for owners. 2.2+ uses `enabled` to switch the Photos UI over.
- `POST /api/immich/password {password}` (owner; `created` accounts only; minimum 8 characters): sets the password through the admin key, so the family can sign in to Immich's web page or app. It's audit-logged, and the password is never stored.

**Automatic:** when Immich is configured, a newly created family (setup, admin invite) is provisioned right after creation. It's best effort: a failure shows on the admin page with a Retry button.

**Startup:** if configured, log the Immich version and warn if it's unreachable or outside the supported range. The server never fails to start because of Immich.

**Isolation suite:** every new route gets a case. Family B can't see or change family A's Immich connection or set its password. Admin routes are admin-only, and the admin key and family keys are never returned by any route.

### Frontend

- **Admin → Immich tab:**
  - A "Server" card: address, admin API key (password field; "saved" state), Test & save, status line with version and supported range.
  - The `ENCRYPTION_KEY` notice when it's missing.
  - A "Families" table: state chip, Immich email, last error, Connect / Retry / Link existing… / Disconnect (typed confirmation), plus "Connect all families".
- **Settings → Family → "Photos (Immich)" card** (owners):
  - Connected or not, with the Immich login email.
  - "Set Immich password" (a kit Modal with a confirm field) for using Immich's own web page or app at home.
  - Members see a one-line status.
- Kit components only; no new `.modal-backdrop` dialogs.

### Tests (TDD, in order)

1. `secretbox.test.ts`: round trip; the wrong key throws `SecretUnreadable`; tampering is detected; `encryptionReady()` handles missing, placeholder and short keys.
2. `immich/version.test.ts`: parse and compare; the supported range at its edges.
3. The stand-in Immich (`test/fake-immich.ts`):
   - An in-memory user, key and session store.
   - Admin versus user permissions, 401/403 like Immich.
   - DTOs shaped like the 3.2.2 spec.
   - A `failNext(op, status)` hook for failure tests.
4. `immich/contract.test.ts`, the **same file** run against the stand-in (default) or a real Immich (`IMMICH_TEST_URL` + `IMMICH_TEST_ADMIN_KEY`). It covers:
   - ping and version;
   - `me` with the admin key;
   - create a user → log in → create a key → `me` with the new key is that user;
   - update the password and log in with it;
   - delete the key → `me` returns 401;
   - a duplicate email is refused.
5. `immich/provision.test.ts` (stand-in + database):
   - provision, and idempotency;
   - a failure part-way, then a retry that reuses the user;
   - link, including refusing a key already linked elsewhere;
   - unlink keeps the account;
   - re-key after an unreadable key.
6. `routes/immich.test.ts`:
   - admin settings validation, where a bad address, a non-admin key or a missing permission gives 400 with a reason;
   - keys never in responses;
   - auto-provision on family creation;
   - owner password;
   - member forbidden;
   - the audit entries.
7. Tenant-isolation cases for every new route.
8. Frontend:
   - the Admin → Immich tab: states, save, errors, connect/link/disconnect;
   - the Settings Immich card: owner vs member, the password modal with its checks.
9. Playwright:
   - the admin connects the stand-in Immich, connects all families, and a family owner sets its Immich password;
   - desktop and phone.

### CI

- `.github/workflows/immich-contract.yml`:
  - Runs on pull requests touching `backend/src/lib/immich/**` or the workflow, nightly, and on demand.
  - Starts Immich 3.2.2 from `ci/immich/docker-compose.yml` (immich-server, its Postgres and Valkey; no machine learning) and waits for `/api/server/ping`.
  - Creates the first admin with `POST /api/auth/admin-sign-up`, logs in, and creates an admin API key (`all`).
  - Runs `vitest run src/lib/immich/contract.test.ts` with the `IMMICH_TEST_*` variables.
