# Phase 1.4 — Tenancy & Access Layer Implementation Plan

**Roadmap:** `docs/superpowers/specs/2026-09-26-completion-roadmap.md` → Milestone 1 → 1.4
**Goal:** One place decides who may see and change what (so 1.5's shared trips extend a single rule instead of forty hand-written `WHERE family_id = $n`), every endpoint validates its input and answers 400/404 instead of 500, a test suite proves no family can reach another family's data through **any** endpoint, families can download their own data, and the schema restarts from one clean baseline with the integrity gaps from the audit closed.

**Decisions this plan relies on (roadmap §2):** test data only (a one-time database reset is fine); multiple families per server; a server admin who can see everything (only by stepping into a family, which is audited); shared trips come next (1.5), so nothing here may assume "a trip's rows all belong to one family".

---

### 1. Errors and input validation (`lib/errors.ts`, `index.ts`)

- `HttpError(status, message)` with `notFound()`, `badRequest()`, `forbidden()`, `conflict()` helpers; routes `throw` instead of hand-building replies.
- One Fastify error handler:
  - `HttpError` → its status; `ZodError` → 400 with the flattened issues; Fastify's own 4xx (empty JSON body, payload too large, multipart limits) pass through with a readable message.
  - Postgres: `22P02`/`22007`/`22008`/`22003`/`23514` (bad UUID/number/date, check constraint) → 400; `23503` (missing reference) → 400; `23505` (duplicate) → 409.
  - Anything else → 500 with a generic message (details only in the log).
- A root `preValidation` hook: any route parameter named `id` or `…Id` must be a UUID, otherwise 404 — before any SQL runs.
- Shared zod pieces (`lib/validate.ts`): `uuid`, `ymd` (a real calendar date, `YYYY-MM-DD`), optional/nullable variants, date-range refinement (end ≥ start). Every body and query that takes a date uses them.

### 2. The access layer (`lib/access.ts`, roadmap §3.2)

- `Scope` = `{ userId, familyId, role, isAdmin }`, built from `req.user` (`scopeOf(req)`). An admin "viewing as" a family has that family's scope, so admin access is exactly what the audit log records.
- An entity registry: kind → table (+ how its family is found for child tables: `packing_item → packing_lists`, `comment → visits`, `waypoint → visits`).
- `loadReadable(kind, id, scope)` / `loadEditable(kind, id, scope)` → the row, or `HttpError(404)` (never 403, so ids don't leak). In 1.4 both mean "my family's row"; 1.5 widens `loadReadable`/`loadEditable` for trip-scoped kinds on shared trips.
- `assertRefs(scope, { trip, theme, person, media, visit, document, … })` → 400 "Unknown trip" etc. unless every referenced id is usable by this family (built-in themes and templates count as usable). Every create/update that stores a reference goes through it.
- `familyWhere(alias, scope)` SQL fragment for list queries (1.5 extends it with shared-trip membership for trip-scoped kinds).
- Every route in `routes/*.ts` is migrated: by-id reads/writes go through `loadReadable`/`loadEditable` (or an `UPDATE/DELETE … WHERE` that includes the family filter and turns "0 rows" into 404), stored references through `assertRefs`, lists through `familyWhere`.

### 3. Tenant-isolation suite (`routes/tenant-isolation.test.ts`)

- Fixture: family A with one of every entity (trip, visit with waypoint, comment, person, media, document with file, theme, icon, map set, itinerary item, blackout, packing list + item, link, share link); family B with its own user.
- A table of every authenticated endpoint → the request family B makes against A's ids, and the expected outcome (404 for by-id routes, 400 for references in bodies, "A's ids absent" for lists/search/stats/export).
- **Completeness check:** the suite collects every registered route (`onRoute`) and fails if one is neither in the table nor on a short, commented exemption list (public routes, admin-only routes covered by `admin.test.ts`, own-account routes).
- After B's attempts, A's rows are re-read and must be unchanged.

### 4. Per-family "download our data"

- `GET /api/family/export` (owners): a `.tar.gz` with `family.json` (the family's rows from every table, grouped by table, no password hashes or tokens) and `files/` (its photos, videos, documents and custom icons). Streams; audited.
- Settings → Family → "Download our data" for owners. The admin's full-server backup stays in Admin.
- The legacy partial `GET /api/export` (map-set JSON) is removed along with the Map header's "Export JSON" entry.

### 5. Migration squash and integrity

- `0001_baseline.sql` replaces `0001`–`0012`: the current schema, cleaned up (no `families.invite_code`, no dead item tables), plus:
  - `CHECK (end_date >= start_date)` on blackouts and trips, `occurred_end >= occurred_on` on visits.
  - Documents have at most one owner: `CHECK (owner_person_id IS NULL OR owner_trip_id IS NULL)`.
  - One packing list per trip **per family** (unique `(trip_id, family_id)` where `trip_id` is set — per family because packing stays private on shared trips).
  - Triggers remove `links` rows pointing at a deleted visit/trip/person/media/document, and `share_links` for a deleted trip — however the row is deleted (directly, or cascaded from a family delete).
  - Missing indexes from the audit: media by family/taken_at and geometry, documents by owner, itinerary by family, links by target.
- The migration runner recognises a database created before the baseline (it has `0001_init.sql` applied) and **refuses to start** with a clear message and the reset steps (README + release notes). No automatic wiping.
- Verified by diffing `pg_dump --schema-only` of (all old migrations) vs (baseline) — the only differences must be the intended ones above.

### 6. Integrity fixes in routes (audit A.2)

- Visit `tripId`/`themeId`, document owners, media `tripId`, itinerary `convertedVisitId`, link endpoints, share targets, packing trip lists: all through `assertRefs`.
- Document PATCH can no longer produce two owners; blackout PATCH checks the merged range; empty `occurredOn` is `null`, not a 500.
- Search escapes `%`, `_` and `\` in `ILIKE` patterns.

### Tests

Backend: error handler mapping (zod, bad UUID param, bad date, FK/unique violations, unknown errors hide details); access helpers (own row, other family's row → 404, built-in theme usable, assertRefs); the tenant-isolation suite with its completeness check; per-family export contents (only that family, no secrets, files included); baseline constraints and cleanup triggers; legacy-database detection. Frontend: "Download our data" button for owners only.
